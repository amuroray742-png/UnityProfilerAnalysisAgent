# 两阶段报告中的手动 Marker 建议

首轮「性能诊断报告」会要求 AI 输出「补充采样建议（手动添加 Marker）」。当现有记录已经足够时，明确说明暂不需要补点；否则优先给出最多 3 条建议。

每条包含：已有帧/线程/调用路径证据、候选补点范围、建议名称、要验证的问题，以及重新录制后应查看的指标。先读完必要的调用树与分页，避免把未查询的样本误当成缺少采样。

第一步没有读取工程源码，因此位置必须标记“待源码确认”，不能提供猜测的文件或行号。选择工程进行后续定位后，才能结合实际代码进一步核对。诊断和定位阶段不会修改代码。用户可以将建议交给程序同事手动添加，也可以在定位完成后选择修改 AI、点击“开始优化”，由新的修改会话确认依据后补 Marker。随后仍需用户复现原操作、重新录制并导入。

技术约束依据 [Unity 6000.3 ProfilerMarker 文档](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Unity.Profiling.ProfilerMarker.html)：建议复用固定名称的 Marker，限定同步区间，避免大量细碎采样或动态名称带来的额外开销。异步调度、执行与等待分别采样，不能让 Auto 范围跨越 await/yield 或线程迁移。

报告中的补点方案是补充证据的建议，不能补回旧录制；实际补点记录与回退沿用[优化项目流程](optimization-loop.md)。纯 Marker 轮次以新增采样能否回答调查问题验收，不代表性能已经改善。报告内容仍需核对，尤其是候选业务阶段与工程版本是否对应。

## 第二阶段：确认具体补点方案

工程联合定位和兼容的 C# 源码定位报告增加「具体 Marker 补点方案」。根据实际读取的源码确认或修正首轮方向，最多给 3 条；已有采样足够、重复包裹无价值时撤回建议。

每条写清：录制证据缺口、相对文件路径与行号、方法及实际代码片段、建议包裹的同步范围、固定名称、待验证问题和重录指标。原始代码与示意代码分开，不生成可应用补丁。确认代码位置不等于证明录制热点由它引起；同名候选、版本不匹配、文件变化仍须说明或重新读取。

纯资源或引擎内部热点只能寻找已读到的业务调用入口，不能往资源文件里加 Marker，也不能猜测不存在的函数。找不到时明确「尚无法给出具体补点位置」。最终定位报告及合并报告的现有导出会一并包含这些建议，无需新导出操作。
